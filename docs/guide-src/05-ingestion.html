Chapter 05plan §6.1–6.4

Being polite to feed hosts

Every briefing starts by fetching feeds from hosts you don't control. If the service asks too often or too clumsily, those hosts throttle or block it, and the briefing quietly loses its sources.

You have seen this happen. Horizon fetched two Reddit feeds in the same minute, Reddit answered 429 Too Many Requests, and the briefing went out without them. The plan's answer is a shared per-host rate limit, honouring Retry-After, backoff with jitter, conditional requests and an identifying User-Agent.

What happens in one fetch

Every step runs as a job in the Postgres queue, and every wait goes back into the queue instead of holding a worker.

  1. Schedule. Once a minute the scheduler selects sources where status = 'active' AND next_fetch_at <= now() and enqueues fetch(source_id) with dedupe_key = 'fetch:{source_id}'. A partial unique index on dedupe_key means a source can never have two fetch jobs queued or running at once.
  2. Take a host slot. The fetch worker asks the per-host limiter when it may send. If the slot is in the future, the job goes back to the queue with run_at set to that slot.
  3. Send a conditional GET. The request carries the validators from the last successful fetch, so an unchanged feed costs almost nothing.
  4. Classify the result. One table in code turns every status code and network error into one action.
  5. Store and hand on. On a 200 the worker parses the feed with feedparser (Hacker News has its own adapter), normalises each entry, and upserts articles and article_sources. For each new or changed original article it enqueues the next job.
  6. Set the next due time. next_fetch_at = now() + fetch_interval, where the interval grows for feeds that rarely change.

Why some articles are extracted before they are scored

Some feeds carry only a short summary, so their sources have extract_full_text set and scoring waits for the full text.

  • No extraction. The fetch worker finds the rubrics of everyone subscribed to this source and enqueues a score job for each (input_hash, rubric_hash) pair not already in llm_scores. The input_hash is a hash of exactly the text the scorer will read.
  • Extraction. The fetch worker enqueues extract(article_id) instead. The extract job runs trafilatura on the article page, stores body_text (truncated to 20k characters), recomputes input_hash, and only then enqueues scoring. So an article is never scored on its summary and again on its full text.
  • Extraction fails for good. If the extract job ends up dead, its failure hook enqueues scoring on the summary, so the article is still scored.

Every enqueue commits in the same transaction as the write it depends on. Extraction is another request to the same host, so it goes through the same per-host limiter.

Turning a response into an action

One explicit table maps every result to a class and every class to one action, with a unit test for each row. The first digit of the status code is only a first guess. 429, 408 Request Timeout and 425 Too Early are all 4xx (client) codes, yet another attempt can fix each of them.

A retryable failure is one where the same request, sent again soon, has a fair chance of working. A fatal one gives the same answer however often you ask, so retrying only wastes the host's capacity and looks like a badly behaved bot. Two rows need a closer look.

  • Counted before acting. A 404 can be a brief mistake during a site deployment, so a source is marked broken only after 5 fatal results in a row. 410 Gone says the removal was deliberate, so it is marked broken at once.
  • Moved. A 301 or 308 updates sources.url, after the new address passes the SSRF guard (the check that refuses private and internal addresses). Temporary redirects are followed for the current request only.
Key principle

Decide what to do from the meaning of each response, written down once in a tested table. Horizon's first bug came from the opposite approach, matching error message text, which broke as soon as the wording changed.

How long to wait before a retry

The plan waits longer after each failure, with a random element, and never sleeps inside the worker. The formula is the same for every queue:

def backoff(n: int, base: float = 2.0, cap: float = 300.0) -> float:
    """n is the attempt that just failed, counted from 1."""
    return random.uniform(0, min(cap, base * 2 ** (n - 1)))

# fetch queue: base = 2 s, cap = 5 min, max_attempts = 4

Exponential backoff doubles the wait after each failure, so a brief blip is retried quickly and a longer outage gets fewer and fewer requests. Retrying at once would add load to a server that is already struggling. The cap stops the wait growing without limit.

min(cap, base * 2 ** (n - 1)) is the ceiling of the wait, and the random draw below it is the jitter. Counting from 1 gives these ceilings:

  • After attempt 1. Up to 2 s.
  • After attempt 2. Up to 4 s.
  • After attempt 3. Up to 8 s, before the fourth and last attempt of this fetch cycle.
  • After attempt 4. No retry. attempts has reached max_attempts, so the job becomes dead and the source waits for its next fetch cycle.

Only base, cap and max_attempts change from queue to queue. Figure 5.3 draws the ceilings to scale.

A retry is a rescheduled job, never a sleep(). The worker sets run_at = now() + backoff(attempts) and puts the job back in queued. It doesn't touch attempts, because the claim already incremented it. The worker is free at once, and a crash between attempts loses nothing.

Why every client needs a different wait

Backoff alone still lets failed clients come back together. If 100 clients fail at the same moment and follow the same fixed schedule, they all retry in the same instant, and the server, just recovered, gets a spike that may knock it over again. This is a thundering herd.

Jitter adds randomness to each client's wait. The plan uses full jitter, where the wait is drawn uniformly from zero up to the ceiling. The name was popularised by an AWS Architecture Blog article on backoff. Both charts below use the same scale.

No jitter: all 100 retries land in the same second.

Full jitter: the same retries spread across 16 seconds.

The total is the same in both charts, but the peak drops from 100 requests in one second to about six a second. The average wait halves too, since a uniform draw from 0 to 16 s averages 8 s.

In your service the herd is your own jobs for many sources on one host, released together after an outage. The per-host limiter spaces those out, and jitter covers load it can't see, such as several hosts behind the same CDN.

When the host says how long to wait

A 429 or 503 may carry a Retry-After header (RFC 9110) that tells you how long to stay away. It comes in two forms, and the parser accepts both:

Retry-After: 120                              # delay-seconds: wait 120 s from now
Retry-After: Wed, 21 Oct 2026 07:28:00 GMT    # HTTP-date: wait until this moment

An HTTP-date depends on two clocks agreeing, so a host with a wrong clock can send a date in the past. Every case reduces to one wait, in code like this:

from email.utils import parsedate_to_datetime

DAY = 24 * 3600

def retry_after_wait(header: str, now: datetime) -> float | None:
    """Seconds to wait, or None to ignore the header and use normal backoff."""
    try:
        secs = float(int(header))                                    # "120"
    except ValueError:
        try:
            secs = (parsedate_to_datetime(header) - now).total_seconds()
        except (TypeError, ValueError):
            return None                                              # "soon"
    if secs < 0:
        return None                          # negative, or a date in the past
    if secs > DAY:
        log.warning("retry_after_anomaly", value=header)
    return min(max(secs, 1), DAY)             # clamp to [1 s, 24 h]

def retry_after_jitter(wait: float) -> float:
    return random.uniform(0, min(60, max(1, 0.1 * wait)))

What the worker then does with a valid wait:

  • Block the whole host, every time. It sets hosts.blocked_until = now() + wait, however long the wait. The host asked the service to stay away, so every source on it waits. Anything over 24 hours is clamped and logged as retry_after_anomaly, so a misconfigured header can't block a host for a year.
  • Waits up to 6 hours. The job is rescheduled for blocked_until plus jitter. This uses an attempt, because a request was made.
  • Waits over 6 hours. This run gives up on the source, logs rate_limited and doesn't retry. Its next_fetch_at is set to at least blocked_until, so the next scheduled fetch can't come early.

The jitter is added on top of the wait, so no client comes back early. It is up to 10% of the wait, at least 1 s and at most 60 s, which spreads out clients given the same second without stretching long waits much.

Worked example

A fetch of www.reddit.com gets a 429 at 07:20:00 UTC on Wednesday 21 October 2026. Here is what six possible headers would do.

  1. Retry-After: 120. The wait is 120 s, so blocked_until is 07:22:00. Jitter is drawn from 0 to 12 s, so the job runs between 07:22:00 and 07:22:12.
  2. Retry-After: Wed, 21 Oct 2026 07:28:00 GMT. The wait is 480 s, blocked_until is 07:28:00, and jitter is 0 to 48 s.
  3. Retry-After: 0. Clamped up to 1 s, so the host is blocked until 07:20:01. Jitter is 0 to 1 s, the 1-second minimum.
  4. Retry-After: 7200 (2 hours). blocked_until is 09:20:00. Ten per cent would be 720 s, so the 60 s maximum applies and the job runs between 09:20:00 and 09:21:00.
  5. Retry-After: soon, -30, or a date of 07:15:00. All are ignored. Nothing is blocked, and the job gets ordinary full-jitter backoff.
  6. Retry-After: 86400 (24 hours). blocked_until is 07:20:00 the next day. The wait is over 6 hours, so this run gives up, fetch_log records rate_limited with retry_after_s = 86400, and next_fetch_at moves to at least 07:20:00 tomorrow.

Sharing one rate limit across every worker

The limit is per host and lives in Postgres, one row per hostname in the hosts table. The default is one request every 2 seconds, and www.reddit.com is seeded with 10 seconds, because both Horizon subreddit feeds hit it in the same minute.

The host is the unit a site operator throttles, and the limit has to be shared because your workers run as several processes. An in-memory limiter only sees its own process, so three processes could each send to Reddit in the same second.

The ticket machine

Think of the ticket machine at a delicatessen counter, which hands out each number exactly once. The hosts row works the same way. next_allowed_at holds the next free slot, and taking a ticket reads it as your slot and moves it on one interval, in one atomic statement:

UPDATE hosts
SET next_allowed_at = GREATEST(now(), next_allowed_at, COALESCE(blocked_until, now()))
                      + make_interval(secs => min_interval_ms / 1000.0)
WHERE host = $1
RETURNING next_allowed_at - make_interval(secs => min_interval_ms / 1000.0) AS my_slot;
  1. The lock. UPDATE … WHERE host = $1 takes a row lock. A second worker waits until the first commits, then works from the row as the first left it, so each slot is handed out once.
  2. The earliest moment. GREATEST(…) picks the latest of now, the next free slot, and the end of any Retry-After block. Postgres's GREATEST ignores NULLs, so the COALESCE mainly states intent.
  3. The next customer. Adding one interval stores the slot after yours. Dividing by 1000.0 keeps fractions of a second.
  4. Your ticket. In RETURNING, columns refer to the updated row, so subtracting one interval gives back the time GREATEST chose. One round trip books the slot and reports it.

Waiting without holding a worker

If my_slot has arrived, the worker fetches now. If it is in the future, the worker stores the slot in the job (payload.host_slot = my_slot), sets run_at = my_slot, and releases the job as a deferral, a release where no work was done.

Sleep until the slot

Workers B and C sit idle for 10 s and 19 s while jobs for other hosts wait. With 20 Reddit jobs, the twentieth sleeps for over three minutes, and a crash mid-sleep strands the job until its lease expires.

Defer to the slot

Worker B releases the job in a few milliseconds and claims a job for another host. The job waits in the queue at no cost, already stored with its new time, so a crash loses nothing.

A deferral doesn't count as an attempt. The claim added 1 to attempts, and the deferral takes it back and adds 1 to deferrals instead, so a busy host can't use up a job's four attempts before a single request is sent. More than 100 deferrals logs job.deferral_storm and raises an alert.

A blocked host works the same way. Before taking a ticket the worker checks blocked_until, and if the host is blocked the job is deferred to blocked_until plus jitter, again without using an attempt.

Using the ticket you already hold

In revision 2, when a deferred job runs again within 30 s after its host_slot, it uses that slot and skips the UPDATE. One request gets one ticket. Revision 3 records a flaw in this rule, and the flaw only makes sense once you know exactly how the rule works.

Without this rule the job could loop for ever. In Figure 5.4, B's first ticket moved next_allowed_at to 06:00:20. A second ticket at 06:00:10 would give B 06:00:20 or a slot after it, so it would be deferred again, and again. With the rule, B arrives at 06:00:10.2, is inside its 30-second window, and fetches.

slot = job.payload.get("host_slot")
if slot is None or now > slot + timedelta(seconds=30):   # no ticket, or it has gone
    slot = take_ticket(host)                              # the UPDATE … RETURNING
    if slot > now:
        return defer(job, run_at=slot, host_slot=slot)    # attempts −1, deferrals +1
fetch(source)                                             # inside our slot

Two cases always take a new ticket. A job more than 30 s late (because of a worker backlog) has lost its slot. A retry after a failed request is a new request.

Why the ticket rule is still open (Q16)

The ticket rule can't guarantee the spacing it promises. A slot is reserved when the job is deferred, but the request is sent whenever a worker next picks the job up, and nothing stops two late jobs from sending together. A design review found two counterexamples.

  • Late jobs bunch up. With a 10 s interval, jobs A, B and C hold slots at 0, 10 and 20 s. A worker backlog delays all three until 25 s. Each is within 30 s of its own slot, so each reuses it, and three requests reach the host in the same second.
  • A shorter window still fails. Cut the grace window to the interval, 10 s. Job A, with slot 0, is picked up at 9 s, and job B, with slot 10, at 10 s. Both are inside their windows, so their requests start 1 s apart.

A shorter window reduces the bunching but can't remove it. The slot records only when a job was allowed to send, and the moment the request actually starts is decided by the queue.

The candidate fix: claim the host just before sending

The plan's candidate fix moves the claim from deferral time to dispatch time. Immediately before sending, the worker runs one conditional UPDATE:

UPDATE hosts
SET next_allowed_at = now() + make_interval(secs => min_interval_ms / 1000.0)
WHERE host = $1
  AND next_allowed_at <= now()
  AND (blocked_until IS NULL OR blocked_until <= now())
RETURNING 1;
  • A row comes back. The host was free, and this worker has just moved next_allowed_at one interval ahead. It sends the request at once.
  • No row comes back. The host is busy or blocked. The job defers to next_allowed_at plus a little jitter (or to blocked_until, if the host is blocked), reserves nothing, and runs the same UPDATE when it comes back.

A claim can only succeed once the previous claim's interval has passed, so successful claims are at least one interval apart. In the first counterexample, A, B and C all try at 25 s. The row lock lets one of them win, the other two defer to just after 35 s, and the jitter decides which of those goes next. The job holds no ticket while it waits, so payload.host_slot and the 30-second window both disappear.

The trade-off is arrival order. Whichever job comes back first after next_allowed_at wins, so one job could in principle keep losing the race. At a few requests a minute per host that's unlikely, and its deferrals count makes it visible, with the alert at 100 deferrals.

This is still a candidate. The plan keeps Q16 open until an integration test passes that delays workers at chosen points and asserts on the recorded request start times in fetch_log.started_at, requiring starts for one host to be at least one interval apart. The test checks start times rather than slot values, because the revision 2 slots were always correctly spaced and the requests still weren't. The limiter is needed by checkpoint 1.2, which makes runs repeatable and recoverable. Checkpoint 1.1 fetches one feed and needs no limiter, so the open question doesn't hold it up.

Common mistake

Taking the slot in the same transaction as the fetch. The row lock lasts until the transaction ends, so every other worker asking for that host would wait for the whole download. Take the slot in its own short transaction, commit, then send the request.

The cost is one database round trip per fetch, about a millisecond, which saves running Redis for a shared limiter (ADR-001, Postgres first).

One 429 pauses the whole host

Because GREATEST includes blocked_until, every new slot for that host starts after the block, whichever source asks. Reddit limits your client as a whole, so a 429 on one subreddit feed means a request for another would probably get one too. A block in the past has no effect, because now() is then larger, so it needs no clean-up. The candidate dispatch-time claim gets the same effect from its blocked_until condition, since no claim can succeed while the block lasts.

Fetching quiet feeds less often

Each source starts at its base_interval of 30 minutes, but many feeds publish once a day. The plan counts unchanged fetches in sources.unchanged_count and stretches the interval when the count reaches 5.

  • Unchanged. A 304, a soft 304 (an identical body), or a 200 with no new or changed articles. It adds 1 to unchanged_count.
  • Changed. Any new or changed article resets unchanged_count to 0 and fetch_interval to base_interval.
  • Five in a row. When unchanged_count reaches 5, fetch_interval doubles, capped at 6 hours, and the count goes back to 0. The next doubling needs another 5 unchanged fetches at the new, longer interval.
  • Failed. A failed fetch touches neither the counter nor the interval. Failures have their own path through retries and consecutive_failures.

Not downloading what hasn't changed

A conditional request asks for the feed only if it has changed since your copy. Most fetches find nothing new, so this saves the host's bandwidth and your parsing time. It works with validators, values the server sends to identify a version.

  • ETag. An opaque quoted string the server chooses, often a hash or version number. A weak ETag, prefixed W/, promises equivalent content without byte-for-byte identity.
  • Last-Modified. The date the resource last changed, to the second.

The rules the plan sets:

  • Store exactly what was sent. The ETag is kept with its W/ prefix and quotes, and sent back as If-None-Match. Last-Modified goes back as If-Modified-Since.
  • Send both. RFC 9110 says a server that gets both must ignore the date, but sending both helps with servers that only support dates.
  • Update validators only from a 200. They describe the version you have processed, and a body-less 304 could hand you a validator for content you never saw.
  • Distrust an impossible 304. A 304 when you sent no validators means a broken server. The plan treats it as a 200 with an empty body and logs a warning.

The soft 304

Many feeds ignore validators, or generate a new ETag on every response, so every fetch returns 200 and the full body. The plan keeps last_body_sha256, and if a new body hashes to the same value it skips parsing and logs unchanged_body.

This soft 304 saves CPU and LLM work but no bandwidth, so the case study reports it separately from real 304s. One number measures the load you put on hosts, the other the work you avoid.

Limits on the HTTP client

Every request goes through one configured httpx client, whose limits protect your workers from slow, broken or hostile hosts.

  • Timeouts. 5 s to connect, 20 s to read. The read timeout applies to each wait for the next chunk, so a slow but steady host is bounded by the size cap instead.
  • Redirects. At most 5, and the SSRF guard checks every hop.
  • Response size. 5 MB, counted while streaming, because Content-Length can be missing or wrong. Counting decoded bytes (iter_bytes()) also catches a small compressed response that expands enormously.
  • User-Agent. briefing-engine/<version> (+https://github.com/simonoconnordev/briefing-engine) names the software and gives operators a URL, with no personal email address to attract spam. A library's default User-Agent looks like an anonymous scraper and is more likely to be blocked.

How this fixes the Horizon Reddit problem

In Horizon, two subreddit feeds on www.reddit.com were fetched in the same minute, the burst got a 429, and nothing slowed down in response. Figure 5.8 maps each part of that failure to a measure in the plan.

Try it
  1. Pick a feed URL from your Horizon config and look at its validators: 
    curl -sI https://example.com/feed.xml | grep -i -E "etag|last-modified"
  2. If you get an ETag, send it back exactly as shown, quotes included: 
    curl -s -o /dev/null -w "%{http_code}\n" -H 'If-None-Match: "the-etag-value"' https://example.com/feed.xml
  3. In psql, build a small hosts table and take three tickets in quick succession by running the UPDATE … RETURNING above three times: 
    CREATE TABLE hosts (host text PRIMARY KEY, min_interval_ms int NOT NULL,
                    next_allowed_at timestamptz NOT NULL, blocked_until timestamptz);
INSERT INTO hosts VALUES ('www.reddit.com', 10000, now(), NULL);
  4. Run UPDATE hosts SET blocked_until = now() + interval '2 minutes'; and take one more ticket.
  5. Open two psql sessions. In the first, run BEGIN and the ticket UPDATE without committing. Run the same UPDATE in the second.
  6. Try the candidate dispatch-time claim. Reset the row with UPDATE hosts SET next_allowed_at = now(), blocked_until = NULL;, run the conditional UPDATE … RETURNING 1 twice within 10 seconds, then once more after 10 seconds.

What you should see, and why:

  • Steps 1 and 2. A 304 means the host supports conditional requests. If you get 200 every time, run step 1 twice and compare the ETags. A value that changes on every request, or no validators at all, means that feed will rely on the soft 304. Record which feeds are which, because that list belongs in your case study.
  • Step 3. The three my_slot values are exactly 10 seconds apart, and the first is the current time. The slots are always spaced correctly. The flaw in Figure 5.5 appears only when the requests are sent.
  • Step 4. The new slot is at or after the block's end, because GREATEST includes blocked_until.
  • Step 5. The second session waits until you commit the first. That is the row lock, and it is why the ticket transaction must stay short.
  • Step 6. The first claim returns one row and the second returns none (UPDATE 0), because the host is busy. After 10 seconds a claim succeeds again. No slot is handed out, so a job that gets no row has nothing to hold while it waits.
If an interviewer asks

"How do you avoid getting blocked by sites you fetch from?"

"I only read published feeds, with an identifying User-Agent. A per-host rate limit in Postgres is shared by every worker. A job that finds the host busy is deferred instead of sleeping. My first design reserved a slot when the job was deferred, and a review showed that late jobs could then send together, so the current candidate claims the host with one conditional UPDATE just before sending, and it isn't settled until a test on recorded request start times passes. Conditional requests and a body-hash check make unchanged feeds almost free. Retryable errors get exponential backoff with full jitter, and Retry-After blocks the whole host. I built it after Reddit sent 429s to the tool I was using, because two of my feeds hit the same host in the same minute."

"Why not just sleep in the worker until the rate limit allows the request?"

"A sleeping worker holds a task slot other hosts' jobs could use, and with many jobs for one host the sleeps add up to minutes. Deferring the job to its slot takes milliseconds and a crash loses nothing. The deferral doesn't use an attempt. In the candidate design the job reserves nothing while it waits, and simply tries the claim again when it comes back."

"How would you prove the rate limiter works?"

"I'd test what the host actually sees. An integration test delays workers at chosen points and checks that the recorded request start times for one host are at least one interval apart. Checking the slot values isn't enough, because my first design handed out perfectly spaced slots and could still send three requests in the same second."

"What if a host sends Retry-After: 86400?"

"The whole host is blocked for 24 hours, which is also the clamp, so a broken header can't block it for longer. Over 6 hours, this run gives up on the source, logs rate_limited, and its next scheduled fetch moves to after the block. Shorter waits reschedule the job for the end of the block plus up to 60 seconds of jitter."
