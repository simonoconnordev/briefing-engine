Running it on AWS

Stage 2 moves the service from docker compose into AWS. One terraform apply into an empty account, plus one pipeline run, must give a working system with nothing set up by hand, and deploys, crashes and database blips must not lose a job.

What runs where

The deployment is one image, two always-on services and one database.

  • ECR (Elastic Container Registry) holds the image and keeps the last 20 versions.
  • api is one Fargate task running FastAPI behind an Application Load Balancer (ALB).
  • worker is one Fargate task running the job loops and the scheduler.
  • RDS PostgreSQL 17 is a single-AZ db.t4g.micro holding the data and the job queue.
  • Secrets Manager, SES and CloudWatch hold secrets, send email, and collect logs, metrics and alarms.

It all sits in a VPC (your own isolated network in AWS) across two availability zones, separate data centres in one region. The ALB and the RDS subnet group both require two.

One image, three commands

The image's ENTRYPOINT is the briefing CLI, with a default CMD of api. Each ECS task definition sets its own command, so one image runs three ways with no environment-variable switches.

  • briefing api starts uvicorn from inside the program, so the server's settings live in code.
  • briefing worker starts the job loops and the scheduler.
  • briefing migrate runs the Alembic migrations and exits.

On Fargate, AWS supplies the machines, so there's no server to patch. A task definition is a versioned template for one container (image, command, CPU, memory, secrets, roles, health check), and each change makes a new revision. A task is one running copy. A service keeps a set number of tasks running and rolls out a new revision when you point it at one.

ECS uses the task execution role to pull the image and fetch secrets before your code starts. Your code runs as the task role, which may only read the named secrets and send through SES.

Why Fargate and not Lambda

ADR-002 chose Fargate because the worker is a long-running process. A Lambda invocation lasts at most 15 minutes and is frozen between events, and three parts of the queue need code that keeps running.

  • Lease heartbeats. A worker extends its job's lease every 20 seconds. If the process is frozen, the lease expires and the reaper hands the job to another worker.
  • LISTEN. Postgres delivers a NOTIFY only to sessions connected and listening when it commits.
  • The scheduler's lock. pg_try_advisory_lock lasts as long as its database session.

Connections are the second problem. Two Fargate tasks with small pools hold a dozen or so. Lambda opens one per concurrent request, so 200 requests at once would exceed the default limit on a 1 GiB db.t4g.micro, roughly a hundred. The usual fix, RDS Proxy, costs extra and pins any client that uses LISTEN to its own connection.

Lambda for this design

About $0 when idle. Needs SQS triggers, an EventBridge schedule, RDS Proxy, API Gateway and a handler adapter. Loses transactional enqueue, LISTEN and the advisory-lock leader. Cold starts, the delay while Lambda creates an environment, land in the reported API p95.

Fargate for this design

About $9 a month per 0.25 vCPU / 0.5 GB task, always on. Runs the queue as designed, with ordinary pooling, the same image as docker compose and no cold starts.

ADR-002 also rejects App Runner, which hides too much for a portfolio piece, and a single EC2 instance, which means managing a server.

How the network avoids a NAT gateway

The ECS tasks run in public subnets with public IPs, and the database runs in private subnets with no route to the internet. That layout needs no NAT gateway, which the plan prices at about $32 a month, the largest single item.

  • Public subnet. Its route table sends internet traffic to an internet gateway, so anything with a public IP can reach out.
  • Private subnet. It has no such route. Outbound traffic needs a NAT gateway, which forwards outbound connections and accepts no new inbound ones.
  • Security group. A stateful firewall, so replies to connections the task opened come back in automatically.

The tasks must reach AWS APIs, feed hosts and Anthropic. Their security groups accept inbound traffic only from the ALB's security group, so outbound calls work and unsolicited packets are dropped.

The database needs no outbound internet, so its two private subnets need no NAT. It isn't publicly accessible, its security group admits only the ECS tasks, and they reach it over the VPC's local route.

The price is defence in depth. With public IPs the security group is the only barrier, so one bad rule, such as a port opened to 0.0.0.0/0 while debugging, exposes a task. The documented production setting is private subnets with NAT. VPC endpoints could replace NAT for AWS services, but the worker would still need NAT for feed hosts and Anthropic.

Key principle

A cost-saving shortcut is defensible when you can say what protection it gives up, what still protects you, and what production would do instead.

The plan proposes this no-NAT layout and about $50 a month always on, but both are open question Q6, still undecided.

Terraform in two roots

Every AWS resource is described in Terraform under infra/, so the environment can be reviewed and rebuilt. ADR-009 picked Terraform because it's common in backend job postings, isn't tied to one cloud, and its plan output reads well in pull requests. CDK in Python is the alternative. Terraform or CDK is open question Q8, and the plan leans towards Terraform.

Terraform keeps a state file mapping each resource in the configuration, such as aws_ecs_service.worker, to the real object in AWS. terraform plan shows what will change, and apply does it. A -/+ (destroy and recreate) on the database means data loss, so plans get read in review.

State lives in S3, so CI and your laptop share one record, with S3's native locking (use_lockfile = true) instead of a DynamoDB table.

Who creates the state bucket

The bucket must exist before anything can keep state in it, so there are two roots.

  • infra/bootstrap/ is applied once, by hand, with admin credentials. It creates the state bucket (versioned, encrypted, public access blocked, prevent_destroy), the GitHub OIDC provider and the CI roles.
  • infra/main/ holds everything else, with its state in that bucket.

Bootstrap starts on local state. After its first apply, terraform init -migrate-state moves that state into the new bucket under its own key, so no local state file is left to lose or commit.

# infra/main/backend.tf (bucket, key and region are placeholders)
terraform {
  backend "s3" {
    bucket       = "<state-bucket>"
    key          = "main/terraform.tfstate"
    region       = "<region>"
    encrypt      = true
    use_lockfile = true   # native S3 locking, no DynamoDB table
  }
}

# infra/bootstrap, once: apply with local state, then move it into the bucket
terraform init && terraform apply
# add backend "s3" { key = "bootstrap/terraform.tfstate" ... }, then:
terraform init -migrate-state

Deploying without stored keys: GitHub OIDC

The pipeline gets AWS permissions through OpenID Connect (OIDC), so no long-lived AWS key sits in GitHub waiting to leak. Each workflow job gets a short-lived signed JWT whose sub (subject) claim says where the job runs and aud (audience) says who it's for. AWS STS checks it against the role's trust policy and returns temporary credentials.

A job that uses a GitHub environment, a named deploy target that can require approval, presents sub = repo:simonoconnordev/briefing-engine:environment:production. The branch isn't in it. The plan uses two roles, both requiring aud = sts.amazonaws.com.

  • Deploy role. It trusts only that environment:production subject. The environment requires your approval and allows only main, so the approval can't be skipped.
  • Plan role. It's read-only and trusts …:pull_request, so pull requests can run terraform plan but never apply.
# Trust policy condition on the deploy role
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub":
      "repo:simonoconnordev/briefing-engine:environment:production"
  }
}

# In the deploy workflow
jobs:
  deploy:
    environment: production
    permissions:
      id-token: write   # allow the job to request an ID token
      contents: read
Common mistake

Writing the deploy role's condition as …:ref:refs/heads/main. A job with an environment never presents that subject, so every deploy fails with access denied. The opposite mistake is StringLike with repo:simonoconnordev/*, which lets every repository you own assume the role.

What happens on a deploy

After CI passes on main and you approve the production environment, the deploy runs in a fixed order.

  1. Tag with the git SHA. 3f9c2ab always means one commit, and it's the version in every log line.
  2. Migrate in a one-off task. briefing migrate runs inside the VPC, so the database never accepts connections from GitHub, and only once, so tasks don't race to migrate.
  3. Roll out. ECS starts each new task beside the old one, waits for its health checks, then drains the old one. A circuit breaker rolls back if new tasks keep failing.
  4. Final gate. The pipeline calls /readyz on the new tasks.

Why old code keeps working after the migration

For a while, old tasks serve against a schema that's ahead of them. So every migration must work with the code before it, and a breaking change uses expand/contract, adding the new form first and dropping the old one only when nothing reads it.

Each migration also sets schema_meta.schema_version to its sequence number. The code declares MIN_SCHEMA_VERSION, the oldest schema it can run on, and /readyz checks schema_version >= MIN_SCHEMA_VERSION.

Worked example
  1. The database is at version 13, and the running release declares MIN_SCHEMA_VERSION = 12.
  2. The new release adds a column in migration 14 and declares MIN_SCHEMA_VERSION = 14.
  3. The migration runs. Old tasks check 14 >= 12 and stay ready.
  4. New tasks check 14 >= 14 and pass the final gate. An exact-match check would have failed every old task as soon as migration 14 finished.

Rollback means redeploying the previous image tag, which is safe because old code works against the newer schema.

Health checks that don't make outages worse

ADR-014 splits the health checks by who acts on them, so a database outage never triggers a restart.

  • GET /healthz (liveness) checks that the process is up and its event loop responds. The ALB target group uses it, so ECS replaces an API task only if that task is stuck.
  • GET /readyz (readiness) runs SELECT 1 within 1 second plus the schema check, and returns 503 naming the failing check. It gates deploys and drives a CloudWatch synthetic alarm, and it isn't wired to the ALB.
  • briefing worker-health is the worker's container check. The main loop touches a timestamp file every iteration, whether or not its database calls worked, so the check fails only if the loop is stuck for 2 minutes.
  • workers.last_heartbeat_at is updated every 15 seconds and only drives the "no heartbeat for 5 minutes" alarm.
Key principle

A health check that ECS acts on must fail only when restarting the task would help. A restart can't fix a database outage. It only adds a restart loop on top of it.

During an outage, API requests that need the database fail within the pool's 2-second connection timeout with 503 problem+json and Retry-After: 5. The worker logs db.unavailable and backs off from 1 second up to 30. When Postgres returns, both carry on.

In a longer outage design A loops, killing each replacement in turn, and every killed worker abandons its jobs until their leases expire.

Shutting down without losing work

ECS stops a task by sending SIGTERM, waiting the stopTimeout of 30 seconds, then sending SIGKILL, which can't be caught. The worker uses that window like this.

  1. At 0 s it stops claiming new jobs.
  2. Up to 25 s running jobs finish, with their heartbeats still extending their leases.
  3. At 25 s it exits and leaves any unfinished jobs, so SIGKILL never arrives.
  4. When those leases expire (60 seconds by default), the reaper requeues the jobs. Idempotent handlers make the rerun harmless.

An API task is first removed from the target group, so the ALB sends it nothing new, and uvicorn finishes the requests in progress.

Common mistake

Writing ENTRYPOINT briefing in shell form. Then /bin/sh is PID 1 and doesn't pass SIGTERM on, so every deploy waits for SIGKILL. Shell form also ignores CMD and the ECS command. Use ENTRYPOINT ["briefing"] and CMD ["api"].

Knowing when it's unwell

The plan watches the system through structured logs, metrics carried inside those logs, and five alarms.

Logs

structlog writes one JSON object per line to stdout, kept in CloudWatch for 30 days. Each line has a stable event name, the git SHA as version, and whichever ids apply, so Logs Insights can filter on fields. Secrets, email bodies and article text are never logged, with a redaction processor as the backstop.

# one log line (wrapped here for reading)
{"ts": "2026-11-08T06:02:14.381Z", "level": "info",
 "event": "fetch.completed", "service": "worker", "version": "3f9c2ab",
 "job_id": 48213, "queue": "fetch", "source_id": 17, "host": "hnrss.org",
 "outcome": "not_modified", "duration_ms": 212}

# Logs Insights: which hosts rate-limited us today?
fields host
| filter event = "fetch.completed" and outcome = "rate_limited"
| stats count(*) by host
SECRET_FIELDS = {"authorization", "api_key", "webhook_secret", "smtp_password"}
API_KEY = re.compile(r"bek_[A-Za-z0-9_]+")   # the plan's API key format

def redact(logger, method_name, event_dict):
    for key, value in event_dict.items():
        if key.lower() in SECRET_FIELDS:
            event_dict[key] = "[redacted]"
        elif isinstance(value, str):
            event_dict[key] = API_KEY.sub("[redacted]", value)
    return event_dict

Metrics

Metrics use CloudWatch Embedded Metric Format (EMF), a log line with an _aws block naming the metric fields, so no agent is needed. Each dimension combination is billed as its own metric, so dimensions stay small, such as queue and outcome, and user_id stays in the log line.

{"_aws": {"Timestamp": 1794117734381,
          "CloudWatchMetrics": [{"Namespace": "<namespace>",
                                 "Dimensions": [["queue"]],
                                 "Metrics": [{"Name": "oldest_queued_job_age_s",
                                              "Unit": "Seconds"}]}]},
 "queue": "build", "oldest_queued_job_age_s": 42}

Alarms

The alarms email you through SNS, each for a failure you'd otherwise notice only as a missing briefing.

AlarmWhat it catches
oldest_queued_job_age_s > 900 on build or deliverWorkers stopped, stuck or overwhelmed, so briefings are at risk of being late
No worker heartbeat for 5 minutesThe worker is down. An alarm on absence must treat missing data as breaching, or silence looks healthy.
Any delivery.deadA delivery used up its retries and needs a replay
5xx rate over 5% for 5 minutesThe API is failing for clients
LLM daily spend over 2× its 7-day averageA runaway loop, a cache bug or a pricing mistake

The case-study figures come from SQL over the ledger tables, such as llm_calls and fetch_log, which stay exact while CloudWatch rolls old metrics up.

What it costs, and tearing it down

The plan estimates about $50 a month always on, plus about $2 of LLM usage.

The ALB, tasks and database bill by the hour even when idle. Running terraform destroy between demos saves money but loses continuous uptime, and that's part of open question Q6. Stage 2 requires one tested destroy and rebuild. Expect these snags.

  • The data goes with the database. Take a snapshot first, because the ledger tables hold your case-study numbers.
  • Secret names stay reserved. Secrets Manager keeps deleted secrets for a recovery window, 30 days by default, so a quick re-apply fails unless it's shortened.
  • The state bucket stays. It belongs to infra/bootstrap/ with prevent_destroy, so destroying infra/main/ never touches it.
Try it

1. Watch a database outage.

  1. Run the stack with docker compose and stop Postgres with docker compose stop db.
  2. Call /healthz, /readyz and GET /v1/articles, then start Postgres and call them again.

While Postgres is down, /healthz returns 200, and the other two return 503 within about 2 seconds, the articles request with Retry-After: 5. Afterwards all three succeed with no restart.

2. Test graceful shutdown.

  1. Enqueue a few slow jobs.
  2. Run docker stop --time 30 on the worker.

It should log its shutdown and exit well before 30 seconds. Exit code 137 means SIGKILL was needed, so check the exec form.

If an interviewer asks

"Why not Lambda? It's cheaper."

"Only when idle. My worker heartbeats leases, listens for Postgres notifications and holds a session-level advisory lock. Lambda freezes between invocations, so I'd rebuild around SQS, lose transactional enqueue, and add RDS Proxy, which pins LISTEN sessions anyway."

"Your containers have public IPs. Isn't that insecure?"

"It saves a $32-a-month NAT gateway. The security groups only accept traffic from the load balancer, and the database is in private subnets with no internet route. I give up defence in depth, and in production I'd use private subnets with NAT."

"Why doesn't your load balancer's health check test the database?"

"ECS replaces tasks that fail it, and that can't fix a database, so a blip would kill every task at once. The ALB checks /healthz, the API returns fast 503s while the database is down, and /readyz gates deploys and drives an alarm."
