The API surface

There is no web UI, so the REST API under /v1 is the whole interface. Clients send an API key, page through articles that keep arriving, retry after timeouts, and in stage 2 submit URLs that your workers will fetch.

Each of those is where a naive API breaks. Keys leak from a stolen database, pages repeat rows, a retry builds the same thing twice, or the server is tricked into reading its own cloud credentials.

What an API key looks like

A key has the format bek_<12-char prefix>_<32 random bytes, base62>. Self-service sign-up and OAuth are non-goals, so the key is the whole of a user's identity.

  • The marker bek_. It gives keys a recognisable shape, so secret scanners such as GitHub push protection and trufflehog can spot them. You can also grep logs and repositories for leaks.
  • The prefix. A unique, non-secret id for the key's row. It appears in GET /v1/api-keys and is safe to log.
  • The secret. 32 bytes from a cryptographically secure source, encoded in base62 (digits and both cases of letters). That fits 256 bits into 43 characters with no punctuation to break when copied.

The full key appears once, in the response to POST /v1/api-keys. DELETE /v1/api-keys/{id} sets revoked_at, and the key stops working on its next request.

Why SHA-256 is enough for API keys

The plan stores SHA-256(secret), a fast hash, although passwords need a slow one such as argon2id or bcrypt (ADR-004). Both rules are right, and the reason is entropy.

Entropy measures how unpredictable a secret is, in bits. A secret with n bits is as hard to guess as one value out of 2n. Human passwords have far less entropy than their length suggests, because people pick words and patterns.

An attacker with your stolen api_keys table can't reverse the hashes, so they hash candidates and compare. A slow hash makes each guess cost more, and it can't add entropy.

For a password, the slow hash is what protects users after a leak. For a 256-bit random secret, brute force is out of reach at any speed, so a fast hash loses nothing and keeps authentication well under a millisecond.

If a reviewer presses, ADR-004 records a cheap extra defence. A pepper computes HMAC(key, secret) with a key from Secrets Manager, so a leaked database alone isn't enough even to check a guess.

Key principle

A slow hash makes up for low entropy and can't create it. Human-chosen secrets need a deliberately slow, memory-hard hash. Machine-generated secrets with 128 bits or more can use a fast one.

How a request is authenticated

The FastAPI auth dependency parses Authorization: Bearer <key>, splits off the prefix and fetches the live key with that prefix:

SELECT id, user_id, secret_hash, scopes, last_used_at
FROM api_keys
WHERE prefix = $1
  AND revoked_at IS NULL
  AND (expires_at IS NULL OR expires_at > now());

Then it hashes the presented secret and compares the two hashes:

presented = hashlib.sha256(secret.encode()).digest()
if row is None or not hmac.compare_digest(presented, row.secret_hash):
    raise unauthorized()        # one 401 for every failure
  • Look up by prefix. The query uses the small UNIQUE(prefix) index, and every key gets a safe public name. Looking up by hash would leave nothing non-secret to log.
  • Compare with hmac.compare_digest. == can stop at the first differing byte, so timing could reveal how much matched. For hashes that leak is nearly useless, but the constant-time function costs nothing.
  • One 401 for every failure. A missing, malformed, unknown, wrong, revoked or expired key gets the same status and body. If "key revoked" differed from "key not found", someone holding an old leaked key would learn it once existed. The detail goes to your logs under the request id.

Scopes, and when to answer 403

Each key has scopes, in stage 2 just read and write, checked by a per-route FastAPI dependency. That's enough to give a dashboard a key that reads briefings but can't change subscriptions or start builds.

A valid key without the needed scope gets 403, problem type insufficient-scope, with the header RFC 6750 defines for this case:

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="write"

401 means "I couldn't establish who you are". 403 means "I know who you are, and this key may not do that", and the header says which scope would.

Recording last_used_at without a write per request

last_used_at shows which keys are still in use, so you can revoke stale ones with confidence. The plan writes it at most once a minute per key.

Each Postgres update creates a new row version that goes to the write-ahead log and must later be vacuumed. A dashboard polling once a second would cause 86,400 writes a day, and the rule caps that at 1,440. Skip the write when the value you just read is recent, and use a conditional update for requests that arrive together:

UPDATE api_keys SET last_used_at = now()
WHERE id = $1
  AND (last_used_at IS NULL OR last_used_at < now() - interval '1 minute');
Common mistake

Logging the raw request while debugging authentication. One logger.debug(request.headers) writes live keys into your log store for its whole retention period. Put the redaction of Authorization and of anything matching bek_ in the logging configuration itself, and test it by logging a fake key.

Why offset pagination breaks on a growing list

Lists such as GET /v1/articles come in pages, with limit defaulting to 50 and capped at 200. Offset pagination asks for page 2 as ORDER BY first_seen_at DESC LIMIT 50 OFFSET 50, and it has two faults:

  • Repeats and gaps. New articles go in at the top of a newest-first list and push everything down, so page 2 repeats rows from page 1. Deletions do the opposite and skip rows.
  • Cost that grows with depth. For OFFSET 100000, Postgres must produce 100,000 rows in order and throw them away.

How keyset pagination continues from the last row

Keyset pagination, also called cursor pagination, asks for the rows after the last one the client saw, identified by its sort key. Articles sort by (first_seen_at DESC, id DESC):

SELECT …
FROM articles
WHERE (first_seen_at, id) < ($t, $id)     -- the last row of the previous page
ORDER BY first_seen_at DESC, id DESC
LIMIT $n + 1;                               -- one extra row, explained below

The condition is a row-value comparison, which compares pairs column by column, like dictionary order. (a, b) < (x, y) is true when a < x, or when a = x and b < y. The id breaks ties between articles that share a first_seen_at, so no row is skipped or repeated at a page boundary.

Worked example

The previous page ended with the row (06:30:00, 12345).

  1. (06:30:00, 12346) is excluded. In id DESC order it came before 12345, so it was on the previous page.
  2. (06:30:00, 12344) is included. Same timestamp, smaller id, so it's the next row after the boundary.
  3. (06:29:59, 99999) is included, because its timestamp is earlier, whatever its id.
  4. A new article at 06:58 is later than the boundary, so it can never appear on this page or shift it.
  • A composite index for each list. The plan gives each paginated list one that matches its sort: articles (first_seen_at, id), briefings (user_id, briefing_date, id) and subscriptions (user_id, created_at, id). A B-tree scans backwards for DESC, so page 1,000 costs the same short scan as page 1.
  • Limit + 1. The query fetches one extra row. If 51 come back for a limit of 50, the server returns 50 and builds next_cursor from the 50th. Otherwise next_cursor is null, and no COUNT(*) was needed.
  • A test of the query plan. GET /v1/articles joins your subscriptions through article_sources to articles. An integration test runs EXPLAIN on the seeded load-test data and fails on a sequential scan of articles.

Offset and limit

Page numbers and a total count. Rows repeat or vanish when data changes, and cost grows with depth.

Keyset with a cursor

Stable under inserts and constant cost at any depth. No "jump to page 7" and no total count, which ADR-008 judges an API client doesn't need.

What's inside a cursor, and why it's signed

The client receives an opaque next_cursor and sends it back unchanged. Its format is <payload>.<sig>:

GET /v1/articles?profile=ai-news&min_score=6&limit=50&cursor=eyJ2IjoxLCJyIjoi…In0.8L1RxbVMkJZMYFuxseMW_g
→ { "data": [...], "next_cursor": "…" | null }

# the payload, decoded from base64url (no padding)
{"v":1,"r":"articles","k":["2026-11-08T06:30:00Z",12345],"f":"609bc063ca879f26"}
  • v, the format version. It lets the format change later.
  • r, the resource. It must match the endpoint, so a briefings cursor can't be used on articles.
  • k, the last row's sort key. These are the $t and $id of the query.
  • f, the filter hash. The first 8 bytes, in hex, of SHA-256 over the canonical query filters. It must match this request's filters, so a client can't change min_score halfway through a walk and silently skip rows.

The signature is base64url of the first 16 bytes of HMAC-SHA256(CURSOR_HMAC_KEY, payload), compared in constant time. Any failed check returns 400, problem type invalid-cursor.

Base64 hides nothing, so without a signature some client would build cursors by hand and the format would become public API. With one, only cursors your server issued are valid, and you stay free to change the sort or encoding. That's what ADR-008 means by not committing the API to a sort implementation. Rotating the key invalidates outstanding cursors, which is acceptable because they're short-lived.

The plan says "canonical filters" without fixing the form. The example hashes {"min_score":6,"profile":"ai-news"} with sorted keys and no whitespace. Pick a form and pin it with a unit test.

How Idempotency-Key makes a retried POST safe

The two POST requests that create work, POST /v1/briefings and POST /v1/deliveries/{id}/replay, accept an Idempotency-Key header. It covers the case where the connection drops and the client can't tell whether the server got the request.

The client generates a UUID once per logical operation and sends it with every attempt. The server keeps it for 24 hours in idempotency_keys:

idempotency_keys
  user_id, key            -- PRIMARY KEY (user_id, key): keys are per user
  request_hash            -- SHA-256 of method, path and canonical body
  state                   -- 'in_progress' or 'completed'
  response_status, response_body
  locked_until, created_at, expires_at   -- expires_at = created_at + 24 h

The handler starts by trying to claim the key. RETURNING tells it whether its insert won:

INSERT INTO idempotency_keys (user_id, key, request_hash, state, locked_until, expires_at)
VALUES ($u, $k, $h, 'in_progress', now() + interval '60 seconds', now() + interval '24 hours')
ON CONFLICT DO NOTHING
RETURNING 1;
  1. Inserted. This request owns the key. It runs the handler, then stores the status and body and sets state = 'completed', in the handler's own transaction where possible.
  2. Different request_hash. The client reused a key for another request, which is a client bug. It gets 422, problem type idempotency-key-reused.
  3. Same hash, completed. A genuine retry gets the stored response with Idempotent-Replayed: true.
  4. Same hash, in_progress. A concurrent request is still running, so this one gets 409 Conflict with Retry-After: 1. The handler never runs twice at once.
  5. Same hash, locked_until passed. The first request crashed. This one takes the key over with UPDATE … WHERE locked_until < now(), which only one request can win, and runs as in case 1.

For POST /v1/briefings, UNIQUE(user_id, profile_id, briefing_date) already prevents a second briefing. The key adds a consistent answer, the same job_id every time.

PUT is idempotent by definition, and the plan keeps it so. A PUT /v1/profiles/{id}/rubric whose canonical hash equals the current version's writes nothing and returns 200 with that version. Going back to an older rubric creates a new version, so history stays linear, and its old cached scores are hit straight away.

Errors in one standard shape

Every error is application/problem+json from RFC 9457, which replaced RFC 7807. Its standard members are type (a URI naming the kind of problem), title, status and detail (this occurrence, for a person to read).

The plan adds request_id to every error, and validation errors list each failing field. In this failure from PATCH /v1/me, the member name errors and the domain are illustrative. The plan names neither, and the domain is still an open question (Q10).

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
X-Request-Id: 0b6f1c2e-6a4d-4f0e-9a51-3c7d2e8f4b10

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "The request body is not valid",
  "status": 422,
  "detail": "1 field failed validation.",
  "request_id": "0b6f1c2e-6a4d-4f0e-9a51-3c7d2e8f4b10",
  "errors": [
    {"field": "timezone", "message": "Not a known IANA timezone name: Europe/Londn"}
  ]
}

With one shape, a client writes its error handling once. It branches on status and type, shows detail, and quotes request_id in a bug report. The id comes from the client's X-Request-Id header or is generated, and it appears in every log line for the request.

How the unsubscribe link works without an API key

From stage 2, every email carries List-Unsubscribe and List-Unsubscribe-Post: List-Unsubscribe=One-Click headers (RFC 8058), pointing at /v1/unsubscribe?token=…. A mail client has no API key, so the token itself proves who is unsubscribing.

token = base64url( user_id ‖ HMAC-SHA256(unsubscribe_key, user_id ‖ "email") )   # ‖ means concatenation

The server splits the token, recomputes the HMAC over the user id and compares with compare_digest. Nobody without unsubscribe_key can make a token for another user.

  • POST does the work. It's the RFC 8058 one-click target, and it sets users.email_enabled = false.
  • GET only asks. It shows a one-line page with a button that sends the POST. Mail scanners follow links in incoming mail, and a GET that unsubscribed would remove people who never clicked.

Webhooks keep working, and the user can turn email back on with PATCH /v1/me. The only other routes without auth are /healthz and /readyz.

SSRF: why accepting URLs is dangerous

In stage 2, users submit feed URLs (POST /v1/subscriptions) and webhook URLs (POST /v1/webhook-endpoints), and your workers request them. Server-side request forgery (SSRF) is an attack in which someone makes your server send a request to a destination they choose.

Your server can reach places the attacker can't, such as private VPC addresses, localhost and the cloud metadata endpoint.

  • EC2. The instance metadata service at http://169.254.169.254/ serves temporary credentials for the instance's IAM role. A server tricked into fetching /latest/meta-data/iam/security-credentials/ and echoing the result hands them over. IMDSv2's session token, obtained with a PUT, blocks most simple SSRF.
  • ECS Fargate, where the plan deploys. Task credentials come from 169.254.170.2, at a path given to the container in an environment variable.

Don't rely on the platform defence alone. Both addresses are link-local, a range the guard blocks.

The guard's three steps

The guard runs when a URL is submitted and again every time a worker connects, because a name's address can change in between.

  1. Resolve the hostname and check every address against the ranges in Figure 10.7. A string check isn't enough, because 127.1, 2130706433, [::ffff:127.0.0.1] and any domain the attacker controls can all lead to loopback.
  2. Check again on every redirect hop. Feed fetches follow redirects by hand, at most 5, each through the same check. Webhook deliveries don't follow redirects at all.
  3. Connect to the address that was checked. The request goes to that IP, with the original hostname in the Host header and the TLS server name (SNI), so virtual hosting and certificate checks still work.

A URL that fails gets 422, problem type url-not-allowed, with the detail "resolves to a non-public address". It doesn't say which address, so nobody can use the endpoint to map your internal DNS.

Why every redirect hop is checked

The attacker submits a URL on their own server, which passes the first check. That server then answers with a redirect to the metadata endpoint, and a client that follows redirects automatically would go there without asking the guard.

A permanent redirect (301 or 308) on a feed updates sources.url only after the new URL passes the guard.

Why the connection goes to the checked IP

A naive guard checks the address and passes the URL to the HTTP library, which resolves the name again to connect. The attacker's DNS answers with a time-to-live of zero, giving a public address the first time and the metadata address the second. This is DNS rebinding, a time-of-check to time-of-use flaw.

With HTTPS the certificate must still be verified against the hostname. With httpx you request the IP and pass the hostname in the Host header and the sni_hostname request extension. Confirm that with a test on the version you install.

Common mistake

Validating the URL with string checks such as "reject localhost and anything starting with 10.". Addresses have many spellings, and any public domain can resolve to a private address. Check the resolved IPs with a real parser such as Python's ipaddress, and connect to the address you checked.

Versioning, and the actions with no endpoint

The base path /v1 promises clients that behaviour won't change under them.

  • Additive changes stay in /v1. A new endpoint, optional parameter or response field is safe if clients ignore fields they don't recognise, which your docs should ask of them.
  • Breaking changes go to /v2. Removing or renaming a field, changing its meaning or making a parameter required needs a /v2 router, served alongside /v1 by the same app.

Creating a user, setting a budget and pausing a source are CLI commands that run against the database, with no HTTP endpoint. As endpoints they'd need an admin key, an internet-facing secret whose theft would expose every user. The CLI needs database credentials that no API client holds.

Try it
  1. In a Python shell, make a key secret in the plan's format, hash it and check it: 
    import secrets, hashlib, hmac, string, base64, json
ALPHABET = string.digits + string.ascii_uppercase + string.ascii_lowercase
def b62(data: bytes, width: int) -> str:
    n, out = int.from_bytes(data, "big"), ""
    for _ in range(width):
        n, r = divmod(n, 62)
        out = ALPHABET[r] + out
    return out
secret = b62(secrets.token_bytes(32), 43)
stored = hashlib.sha256(secret.encode()).digest()
hmac.compare_digest(hashlib.sha256(secret.encode()).digest(), stored)   # True
  2. Build and verify a cursor in the plan's format, then tamper with it: 
    KEY = b"dev-only-cursor-key"
def b64(b: bytes) -> str: return base64.urlsafe_b64encode(b).rstrip(b"=").decode()
def sign(p: str) -> str: return b64(hmac.new(KEY, p.encode(), hashlib.sha256).digest()[:16])
f = hashlib.sha256(b'{"min_score":6,"profile":"ai-news"}').digest()[:8].hex()
payload = b64(json.dumps({"v": 1, "r": "articles", "k": ["2026-11-08T06:30:00Z", 12345],
                          "f": f}, separators=(",", ":")).encode())
cursor = f"{payload}.{sign(payload)}"
def valid(c: str) -> bool:
    p, s = c.rsplit(".", 1)
    return hmac.compare_digest(s, sign(p))
valid(cursor), valid("A" + cursor[1:])          # (True, False)
base64.urlsafe_b64decode(payload + "==")       # readable by anyone
  3. Try the address checks: ipaddress.ip_address("169.254.169.254").is_global and ipaddress.ip_address("224.0.0.1").is_global.

The key check prints True, and False if you change one character of secret. The cursor decodes to plain JSON, which is why it must be signed, and the tampered copy fails verification. The metadata address gives False, but the multicast address gives True, which is why the guard needs its own multicast check.

If an interviewer asks

"Why store API keys with SHA-256 when you'd use argon2 for passwords?"

"Slow hashes make guessing low-entropy, human-chosen secrets expensive. My keys are 256 random bits, so there's nothing to guess at any speed, and a fast hash keeps auth under a millisecond. Lookup is by a non-secret prefix with a constant-time compare. Against a leaked database alone I'd add a pepper from Secrets Manager, at almost no cost."

"A user subscribes to http://169.254.169.254/latest/meta-data/. What happens?"

"The guard resolves it, sees a link-local address, and rejects it with a 422 that doesn't name the address. The check repeats on every redirect hop, and the connection goes to the checked IP, so neither a redirect nor DNS rebinding gets round it. Fargate's credential endpoint, 169.254.170.2, is in the same range."

"Two requests with the same Idempotency-Key arrive at once. What happens?"

"Both insert the key row with ON CONFLICT DO NOTHING, and the primary key lets one win. The other sees in_progress and gets 409 with Retry-After: 1. Its retry gets the stored response with Idempotent-Replayed: true. If the winner crashed, its 60-second lock expires and the next request takes the key over."
