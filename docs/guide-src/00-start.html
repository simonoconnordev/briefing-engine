The briefing engine

Every morning at 06:30, an email arrives in your inbox with the day's most relevant AI and technology news, ranked and summarised. At the moment that email is produced by Horizon, an open-source news aggregator that runs on your own machine as a Windows scheduled task. The briefing engine is its replacement: a service written from scratch that does the same job for any number of users, and does it in a way that you can explain and defend line by line.

Where the project comes from

Horizon reads 14 RSS feeds and the Hacker News top stories with a score of at least 100. It asks claude-sonnet-5-5 to score each item under two profiles, ai-news with a threshold of 6.0 and tech-blog with a threshold of 5.0, extracts the full text of some articles with trafilatura, and sends the result over SMTP. It works well, but it is mostly configuration, and getting it to run reliably exposed three bugs that you fixed upstream.

Each of those bugs revealed a design requirement that the briefing engine now takes as a starting point. Anthropic's API rejected the temperature parameter and Horizon's fallback did not recognise the error, which showed that the system should send only the parameters the API needs and should sort errors by kind instead of matching message text. Reddit's RSS endpoint returned 429 Too Many Requests when requests arrived in bursts, which showed the need for per-host rate limits, respect for Retry-After and backoff with jitter. Finally, the email's HTML was escaped twice, so apostrophes appeared as &#x27;, which showed that escaping must happen in exactly one place and be tested against known output.

What the briefing engine does

The service collects articles from a shared set of sources, judges each one against the interests of each user, and turns the best of them into a short written briefing. Figure 0.1 follows that journey from left to right.

The split between shared and personal data is what allows the service to grow. If two users follow the same feed, it is fetched once, and if they use the same rubric, each article is scored once. The cost of fetching and scoring therefore rises with the number of distinct sources and rubrics, and it stays roughly flat as more users subscribe to them.

The two models have different jobs. Claude Haiku 5.5 handles the high-volume work of scoring every new article, because that work needs to be fast and cheap. Claude Sonnet 5.5 writes the final summary, which happens only once per user each day and benefits from a stronger writer. Users interact with the service through a REST API and receive the result by email or, if they prefer, as a signed webhook that their own software can verify.

What makes it a serious backend project

A script that fetches feeds and calls a model would fill the inbox most mornings. The briefing engine is built to keep doing so when things go wrong, and that ambition shapes three ideas that run through the whole design.

The first idea is that PostgreSQL holds everything. The articles, scores and briefings live there, and so do the job queue, the rate-limit state and the budgets. Because all of this state shares one database, a step can record its result and schedule the next piece of work in a single transaction, so the system never ends up half updated after a crash.

The second idea is that every step is safe to repeat. Crashes, timeouts and retries mean that some work will inevitably run more than once, so each step is designed to produce the same result the second time. Re-running an entire day should send no duplicate email and cost close to nothing, because the expensive model calls are cached.

The third idea is that failure is planned for. Feeds go offline, hosts impose rate limits and models occasionally return output that cannot be used. The plan decides in advance how the system responds to each of these cases, and it keeps cost under control by recording every model call and, from stage 3, enforcing a budget for each user that concurrent jobs cannot overspend.

Some things are deliberately left out so that the project stays small enough to understand completely. There is no web interface, no self-service sign-up and no scraping of content that sites do not offer through their feeds. The service runs in a single AWS region without a high-availability guarantee, and the plan notes where a production system would differ.

How it will be built

The design is written down in docs/plan.md before any code exists. Two design reviews of an earlier revision found that it asked for too much before the first briefing could arrive, so the plan now follows one working rule: settle what the next step needs, and record later decisions without building them early.

The first stage, which replaces Horizon for your own briefing, is therefore built in four checkpoints. Each one ends in something you can run and inspect, so a problem can be traced to the layer just added.

  • One complete briefing. A single feed travels through the real job queue, is scored by Haiku with its cost recorded, and arrives as a simple email. You run it by hand.
  • Repeatable and recoverable. The same narrow path learns to cache, deduplicate, retry and survive a worker being killed at chosen points, and re-running a day makes no model calls and sends nothing.
  • Your actual daily briefing. All the feeds, both profiles, the Sonnet write-up and daily scheduling arrive, and the system handles your normal reading load for a week.
  • Horizon replacement. The engine runs alongside Horizon for seven days. It is finished when the briefing has arrived by 06:30 on seven consecutive days at a quality you judge at least as good, and you switch Horizon off yourself.

Reading quality is judged from the very first email. After each one you note what was useful, what was misleading or annoying, and one thing you would change, and those notes decide what to build next. Automated checks are added only when the notes show a problem that keeps recurring.

The second stage turns the engine into a multi-user service on AWS. Terraform creates the infrastructure from an empty account, a CI pipeline deploys it after your approval, and a second test user receives their own briefing while sharing fetches with you and seeing none of your data.

The third stage adds the features that make the design measurable: shared caching across users, enforced budgets, signed webhooks with retries, and a load test. It ends with a published case study that reports real numbers for cost per briefing, cache savings, API latency and recovery from deliberate outages.

All of this rests on a clear picture of how work moves through the system during a single day, which is where the explanation begins.
