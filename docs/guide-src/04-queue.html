The job queue

Every stage of the pipeline hands work to the next through one table, jobs. So the queue decides whether a briefing arrives on time, whether a crash loses work, and whether a retry sends an email twice. It has to be built so that every job still reaches a final state, even when a worker dies or stalls halfway through. You write it yourself (ADR-003). The core is a few hundred lines, but the responsibility is larger than that suggests, so the plan proves recovery on a narrow path before other features depend on it.

Why the work goes through a queue

Every step of a day depends on feed hosts, the Anthropic API or a mail or webhook endpoint, and each fails some of the time. A single script that runs the day top to bottom handles that badly. A crash loses the remaining work, and a retry is a sleep() that holds up everything behind it.

A queue records each piece of work as a row before anyone does it, which gives you four things:

  • Durability and retries. A failed job goes back into the table with a future run time. A crash loses nothing, because the job is still a row.
  • Spreading load. Three hundred new articles become many score jobs that several workers run in parallel.
  • Priorities. Delivery outranks fetching, so a fetch backlog can't delay your email.
  • Visibility. SELECT state, count(*) FROM jobs GROUP BY state is a working dashboard from day one.
Key principle

Record the decision to do work durably, in the same database as the data, before doing the work. Leases, retries and dead letters all exist to make sure a recorded job reaches a final state without anyone remembering it in memory.

What a job row holds

A job is one row in jobs. Figure 4.2 shows a fetch job for source 42 that timed out once and is now on its second attempt.

ColumnWhat it's for
idA bigint identity. Logs, dead letters and the replay command refer to it.
queueWhich pool of worker slots runs the job: fetch, extract, score, build, deliver or maintenance.
kind, payloadWhich handler to run, and its arguments as jsonb. Payloads hold ids, never whole articles, so the handler always reads current data.
dedupe_keyWhile one job with a given key is queued or running, a second can't be inserted. Every kind of job has one.
group_keyThe rubric hash, on score jobs only. It lets a worker claim ten jobs for one rubric as a batch.

priority, run_atOrder and eligibility. A job is claimable only once run_at <= now(), which is how retries and deferrals wait.
attempts, max_attempts, deferralsRuns that actually started work, the limit after which the job goes dead, and how often it was put back without doing any work.
locked_by, lease_expires_atWhich worker owns a running job, and until when. The reaper reads these.
last_error, created_at, finished_atWhat went wrong last time, and how long the job waited and ran.

A partial index is an index with a WHERE clause, so it holds only the rows that match. The plan defines four on jobs:

  • Dedupe. UNIQUE(dedupe_key) WHERE state IN ('queued', 'running') stops duplicate pending jobs.
  • Claim. INDEX(queue, priority DESC, run_at) WHERE state = 'queued' matches the claim query, so finding the next job never touches finished rows.
  • Score batches. INDEX(queue, group_key, run_at) WHERE state = 'queued' serves the batched score claim.
  • Reaper. INDEX(lease_expires_at) WHERE state = 'running' finds expired leases.

What Postgres does when two writers want the same row

Readers never wait for writers, but two writers of the same row take turns. The claim query relies on both facts.

  • Row versions (MVCC). Under multiversion concurrency control, an UPDATE writes a new version of the row, and each statement reads a snapshot. Old versions stay as dead tuples until VACUUM reclaims them.
  • Row locks. An update locks the row until its transaction ends, and a second writer waits. When the first commits, Postgres (at the default READ COMMITTED level) re-reads the newest version and checks the waiter's WHERE clause again. If the row no longer matches, the waiter skips it.
  • FOR UPDATE. SELECT … FOR UPDATE takes the same lock without changing anything. Plain SELECTs are unaffected.

Claiming work with SKIP LOCKED

Several workers ask for work at once. Two must never get the same job, and none should wait for another. Selecting a job and then updating it leaves a gap in which two workers pick the same row, and FOR UPDATE closes the gap.

FOR UPDATE on its own

Every worker sorts the same way, so all of them try to lock the same first row. One wins and the rest wait, then collide again on the next row.

FOR UPDATE SKIP LOCKED

A row another transaction has locked is skipped at once. Each worker locks a different set of rows, nobody waits, and each extra worker adds throughput.

The claim query, line by line

WITH next AS (
  SELECT id FROM jobs
  WHERE state = 'queued' AND queue = ANY($queues) AND run_at <= now()
  ORDER BY priority DESC, run_at
  LIMIT $batch
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j
SET state = 'running', attempts = attempts + 1,
    locked_by = $worker_id, lease_expires_at = now() + $lease
FROM next WHERE j.id = next.id
RETURNING j.*;
  1. WITH next AS (…) is a named sub-query that the UPDATE joins against. Select and update are one statement, so the claim is one short transaction.
  2. WHERE picks jobs that are waiting, in a queue this worker has free slots for, and due. A retry scheduled for 06:31 stays invisible until 06:31.
  3. ORDER BY priority DESC, run_at takes the most important, longest-waiting work first, in the order of the partial index.
  4. LIMIT $batch takes several jobs in one round trip, typically one per free slot.
  5. SET marks the job taken, with its owner and a 60-second lease. It's also the only place attempts goes up, so a run that crashes is still counted.

Skipping means strict ordering across workers isn't guaranteed. That's the price of never waiting, and it doesn't matter here.

Claiming score jobs ten at a time

One Haiku call scores up to 10 articles under one rubric, so score jobs carry group_key = rubric_hash. A score worker first locks the oldest due group with SELECT group_key … ORDER BY priority DESC, run_at LIMIT 1 FOR UPDATE SKIP LOCKED, then runs the claim with AND group_key = $g and a batch of 10.

Serving the oldest group first means a busy rubric can't starve the others.

Leases, heartbeats and the reaper

The claim commits straight away, and the job runs with no transaction open. A lease is how the queue gets the job back if the worker dies.

Holding the claim transaction open would also recover crashes, but every running job would hold a connection, and a long-open transaction stops VACUUM removing dead tuples anywhere in the database.

  • Lease. A time limit on a worker's claim to a job. The claim writes lease_expires_at = now() + 60 s.
  • Heartbeat. Extends the lease every lease / 3, or 20 seconds, so two heartbeats in a row can fail before it lapses.
  • Reaper. Part of the scheduler loop. On each tick it handles jobs whose lease has run out.

The plan gives no SQL for these. One straightforward version:

-- job heartbeat, every lease / 3
UPDATE jobs
SET lease_expires_at = now() + $lease
WHERE id = $job_id AND state = 'running'
  AND locked_by = $worker_id;   -- 0 rows: you no longer own this job

-- reaper, on each scheduler tick: lock the expired jobs
SELECT id, attempts, max_attempts FROM jobs
WHERE state = 'running' AND lease_expires_at < now()
FOR UPDATE SKIP LOCKED;

-- then, per job, in the same transaction
UPDATE jobs
SET state = 'queued', run_at = now() + $backoff,   -- or 'dead' at max_attempts
    last_error = 'lease expired', locked_by = NULL, lease_expires_at = NULL
WHERE id = $id AND state = 'running' AND lease_expires_at < now();

The locked_by guard means a worker that has lost its job changes nothing, and the zero row count tells it to stop.

A lease expiry counts as an attempt, because the crashed run did start work. If attempts has reached max_attempts, the reaper sends the job to dead instead.

Worst-case recovery is the lease, plus the wait for the next reaper tick, plus the retry's backoff. That's ample for a briefing built 30 minutes before its send time.

Common mistake

Calling the LLM between SELECT … FOR UPDATE and COMMIT. It works in testing, but under load it exhausts the connection pool and blocks vacuum. Claim, commit, then work.

The four job states, and how attempts are counted

A job is queued, running, succeeded or dead. There is no failed state. A failure that will be retried goes back to queued with a future run_at, and one that won't becomes dead.

Every change of state is one UPDATE, guarded by the state it expects to leave. The plan's attempt accounting:

EventattemptsdeferralsNext state
Claimed+1, here and only hererunning
Succeededsucceeded
Retryable failure, attempts < max_attemptsunchangedqueued, run_at = now() + backoff(attempts)
Retryable failure at max_attempts, or a fatal errorunchangeddead, plus a dead_letters row
Deferral: host slot in the future, or host blocked−1, giving back the claim's +1+1queued, run_at = slot
Lease expiredunchanged: the crashed run countsReaper: dead at max_attempts, otherwise queued with backoff

So attempts means "runs that actually started work". A fatal error, such as a feed that answers 404, goes straight to dead.

  • Poison pills. A job that crashes its worker every time is counted by the reaper and stops at max_attempts, instead of crashing workers for ever.
  • Deferral storms. A deferral costs no attempt, so a job that defers in a loop never dies. Over 100 deferrals logs job.deferral_storm and alerts.

Every finishing write carries the guard AND locked_by = $worker_id AND state = 'running'. A worker whose lease has gone discards its result, so it can't overwrite a job another worker may now own.

Why a slow worker can run a job twice

The queue is at-least-once, so a job can occasionally run twice. Exactly-once isn't possible when the work has effects outside the database, such as an email, because no transaction covers both systems.

At-most-once

Record completion, then act. A crash in between means the work never happens. For a daily briefing, silently losing an email is the worse failure.

At-least-once

Act, then record completion. A crash in between means the work happens twice. If every handler is idempotent, that does no harm.

A crash is the obvious way to get a second run. The subtler one is a worker that is alive but slow, for example because CPU-heavy code blocks the event loop the heartbeat runs on. A lease can't tell it from a dead one.

The guard keeps the job's record correct, and idempotent handlers keep the effects correct. A second score run finds the cached score, and a second build finds the existing briefings row. Email receivers can't deduplicate, so a rare duplicate email is possible, a trade-off the plan documents openly.

Key principle

A queue can't tell a dead worker from a slow one, so any queue that recovers from crashes will sometimes run a job twice. Make every handler idempotent so that running twice has the effect of running once.

Enqueueing in the same transaction as the data

A fetch worker saves an article and must also enqueue its score job. With the queue in another system, such as SQS, those are two writes that no transaction spans, and a crash between them breaks either order:

  • Commit, then send. The article is saved but never scored, and nothing records the missing job.
  • Send, then commit. A score worker receives a job for an article that doesn't exist.

The usual fix is a transactional outbox. The worker writes the message into an outbox table with the data, and a relay process publishes it. That adds a table, a process and a second system that fails on its own.

With the queue in the same database, enqueueing is an ordinary INSERT in the transaction that writes the data. This is the main reason ADR-001 chooses Postgres.

BEGIN;
INSERT INTO articles (url_hash, url_canonical, content_hash, input_hash, title, …)
VALUES (…)
ON CONFLICT (url_hash) DO UPDATE SET last_seen_at = now(), …
RETURNING id, (xmax = 0) AS inserted;

-- for each (input_hash, rubric_hash) not already in llm_scores
INSERT INTO jobs (queue, kind, payload, dedupe_key, group_key, priority)
VALUES ('score', 'score', $payload,
        $dedupe_key,                -- 'score:{rubric_hash}:{input_hash}'
        $rubric_hash, $score_priority)
ON CONFLICT DO NOTHING;

NOTIFY jobs_score;
COMMIT;   -- the article and its score jobs appear together, or not at all

If the worker crashes before COMMIT, both vanish and the fetch simply runs again.

Retries and host deferrals

A job that fails with a retryable error is rescheduled in its own row, and the slot is freed. A worker never sleeps holding a job, so no slot idles and a restart loses no retry.

UPDATE jobs
SET state = 'queued',
    run_at = now() + $delay,        -- backoff with jitter, computed in Python
    last_error = $error,
    locked_by = NULL, lease_expires_at = NULL
WHERE id = $job_id AND state = 'running' AND locked_by = $worker_id;

This leaves attempts alone, because the claim already counted the run. The delay is "full jitter", uniform(0, min(cap, base × 2^(n−1))), where n is the attempt that just failed, counted from 1. Every queue uses this formula with its own base, cap and max_attempts. Fetch uses a 2 s base, a 5 min cap and 4 attempts per fetch cycle.

Worked example

One fetch job for source 42, with a 5-second connect timeout:

  1. 06:00:00. Attempt 1 times out at 06:00:05. The ceiling is 2 s and the draw is 1.3 s, so run_at is about 06:00:06.
  2. 06:00:06. Attempt 2 gets 503 with no Retry-After. The ceiling is 4 s and the draw is 2.9 s.
  3. 06:00:09. Attempt 3 gets 429 with Retry-After: 120. hosts.blocked_until becomes 06:02:09, and the job waits until then plus up to 12 s of jitter (10% of the wait), say 7.5 s.
  4. 06:02:17. Attempt 4 succeeds. Had it failed, the job would have gone dead with attempts = 4.

A host deferral gives the attempt back

Before fetching, a worker asks the per-host rate limiter for a slot. If the slot is in the future, the job is deferred. No request was made, so no attempt is used.

UPDATE jobs
SET state = 'queued', run_at = $slot,
    attempts = attempts - 1, deferrals = deferrals + 1,
    payload = payload || jsonb_build_object('host_slot', $slot),
    locked_by = NULL, lease_expires_at = NULL
WHERE id = $job_id AND state = 'running' AND locked_by = $worker_id;
  • One ticket per request. In revision 2, a job that runs within 30 seconds after its stored host_slot uses that slot, because asking again would give it a slot further out each time. Reserved slots can still bunch up when jobs resume late, so the rule is under revision (Q16), and the candidate fix claims the host just before sending and stores no slot at all.
  • Blocked hosts. While hosts.blocked_until is in the future, every job for that host defers to it plus jitter.
  • The job that got the 429. It did make a request, so its reschedule counts as an attempt.

One pending job per key

A partial unique index allows at most one queued or running job per key. Without it, the scheduler's next one-minute tick would enqueue a slow fetch a second time.

CREATE UNIQUE INDEX jobs_dedupe_pending ON jobs (dedupe_key)
  WHERE state IN ('queued', 'running');

INSERT INTO jobs (queue, kind, payload, dedupe_key, priority)
VALUES ('fetch', 'fetch', '{"source_id": 42}', 'fetch:42', $fetch_priority)
ON CONFLICT DO NOTHING;   -- a second pending fetch for source 42 is dropped

Every kind of job has a key:

Queuededupe_key
fetchfetch:{source_id}
extractextract:{article_id}
scorescore:{rubric_hash}:{input_hash}
buildbuild:{user_id}:{profile_id}:{briefing_date}
deliverdeliver:{delivery_id}
maintenancemaint:{task}:{utc_date}

A finished job is outside the partial index, so the next fetch for source 42 inserts normally. If you name a conflict target, repeat the predicate: ON CONFLICT (dedupe_key) WHERE state IN ('queued', 'running') DO NOTHING.

If two inserts with the same key race, the second waits for the first transaction, then does nothing if it committed or goes ahead if it rolled back. A "check, then insert" in Python can't settle a race that way.

Common mistake

Writing a plain UNIQUE(dedupe_key) without the WHERE clause. Finished jobs stay in the table for days, so the first job for each key would block every one after it.

Waking workers with LISTEN and NOTIFY

Workers wake within a second of an enqueue. A session that runs LISTEN jobs_score receives every NOTIFY jobs_score, and an idle worker waits on that with psycopg 3.

  • Sent only on commit. A worker never wakes for a job that doesn't exist yet, and a rollback sends nothing.
  • Merged. Identical notifications from one transaction may arrive as one. The worker claims a batch, so that's fine.
  • Not stored. A worker that is reconnecting at the time never receives it.

So the plan keeps a 5-second poll as a fallback. It also catches retries, which fall due with no notification.

Exactly one scheduler

Every worker contains the scheduler loop, and a Postgres advisory lock decides which one runs it. That's a lock on a number your code chooses, which only one session can hold at a time.

SELECT pg_try_advisory_lock($scheduler_lock_id);   -- true: you lead; false, at once: you don't

The lock lasts until the session ends, which gives you failover. The leader enqueues due fetches, reaps expired leases, releases expired budget reservations, and enqueues build_briefing at each user's send_time minus 30 minutes in their timezone.

  • Use a dedicated connection. A lock taken on a pooled connection goes back to the pool with it.
  • Call it once. These locks stack, so a leader that calls again must unlock twice.
  • Expect brief overlaps. After a silent network failure, Postgres may not notice the session has gone until TCP keepalives time out.

An overlap is harmless, because duplicate fetches and builds collide on their dedupe keys and on UNIQUE(user_id, profile_id, briefing_date). The lock prevents wasted work; the constraints guarantee correctness.

Priorities and the extract queue

The queues are ordered deliver > build > score > extract > fetch. The closer a job is to something the user is waiting for, the sooner it runs, so a fetch backlog can never delay a briefing.

For sources with extract_full_text set, the fetch enqueues extract(article_id) in place of scoring. The extract job fetches the page through the same host limiter, stores body_text, recomputes input_hash and only then enqueues scoring, so an article is never scored twice.

If an extract job goes dead, a failure hook enqueues scoring on the summary. Extract ranks above fetch so that extraction finishes before more fetches pile up.

Strict priority can cause starvation, where steady high-priority work blocks low-priority work for ever. At a few builds per user per day it can't happen here, but be ready to name it.

Dead letters and replay

A job that goes dead gets a dead_letters row holding the job id, the exact payload and the last error. Nothing retries it automatically, because a job that failed every attempt usually points to a broken feed or a bug. Once you've fixed the cause, briefing jobs replay <id> works on the same job row:

  1. Reset. It sets state = 'queued', attempts = 0, deferrals = 0 and run_at = now().
  2. Mark. It sets replayed_at on the dead letter, which drops it from the unresolved list.
  3. Refuse a duplicate. If another live job with the same dedupe_key exists, the unique index rejects the update. Replay reports "an equivalent job is already queued: #id" and changes nothing, because that job will do the same work.

Deliveries use the same table with kind = 'delivery', and their replay resends with the same event id.

How long rows are kept

A maintenance job deletes old rows in modest batches:

  • Succeeded jobs after 7 days.
  • Dead jobs and their dead letters 30 days after the job died. A replayed job's dead letter goes 7 days after the replay.
  • Delivery dead letters after 90 days, because a user may want to replay them after a long outage.

Every claim, heartbeat and finish leaves a dead tuple. Because state and lease_expires_at are indexed, these updates can't use the heap-only tuple (HOT) shortcut, so each adds index entries too. At a thousand jobs a day autovacuum barely notices. At 100× in the load test it might, which is why vacuum lag on jobs is a switch condition.

The worker process

Each container runs one worker process with one asyncio event loop, because fetches and LLM calls mostly wait on the network. It has fixed slots per queue, for example fetch 8, score 4, build 2 and deliver 4, plus a pool for extract. Fixed slots isolate the queues and limit the load on each external service.

Shutting down on SIGTERM

On a deploy, ECS sends SIGTERM, waits 30 seconds and then sends SIGKILL. The worker stops claiming, gives jobs in progress up to 25 seconds, and exits. Anything still running is left for the reaper, with the attempt counted, so shutdown reuses the tested crash path.

Liveness, heartbeats and a database outage

  • Job heartbeat. Extends one job's lease every 20 seconds, for recovery.
  • Worker heartbeat. Writes workers.last_heartbeat_at every 15 seconds, for monitoring. An alarm fires after 5 minutes without one.
  • Container health check. briefing worker-health checks a timestamp file the main loop touches on every iteration, whether or not the database answered. It fails only if the loop is stuck for over 2 minutes.

The health check ignores the database on purpose, because a restart can't fix a database outage (ADR-014). During one, the loop logs db.unavailable and backs off from 1 s, doubling to 30 s. Running jobs finish or fail their final write, and the reaper retries them once Postgres is back. ECS leaves the task alone, and the heartbeat alarm fires next to the RDS alarm.

Postgres or SQS

ADR-001 also weighed Redis-based libraries (RQ, Celery, arq), but SQS is the comparison you'll defend most often.

Postgres wins on atomicity, simplicity and inspection, and SQS on throughput and isolation. The coupling matters less than it looks, because workers can't do useful work while the database is down anyway.

The plan keeps Postgres in all three stages, behind a Queue interface, with a switch condition. The stage 3 load test measures claims at 10× and 100× the expected volume. A p95 claim time over 50 ms, or vacuum lag on jobs, would move deliver to SQS first, because it gains most from isolation and least from transactional enqueue.

ADR-003 records writing the queue instead of using procrastinate, a mature Postgres queue for Python. The risk is subtle lease and retry bugs. The mitigation is concurrency tests, such as four workers draining 1,000 jobs with each running exactly once.

Try it: see SKIP LOCKED with your own eyes
  1. Start a throwaway Postgres with docker run --rm -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres:17 and open two psql windows.
  2. In window 1, lock one row and leave the transaction open: 
    CREATE TABLE jobs (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                   state text NOT NULL DEFAULT 'queued');
INSERT INTO jobs (state) SELECT 'queued' FROM generate_series(1, 5);

BEGIN;
SELECT id FROM jobs WHERE state = 'queued' ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED;   -- returns 1
  3. In window 2, try both kinds of lock: 
    BEGIN;
SELECT id FROM jobs WHERE state = 'queued' ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED;   -- returns 2 immediately
ROLLBACK;

BEGIN;
SELECT id FROM jobs WHERE state = 'queued' ORDER BY id LIMIT 1
FOR UPDATE;               -- hangs
  4. In window 1, run UPDATE jobs SET state = 'running' WHERE id = 1; COMMIT;. Then type ROLLBACK; in window 2.

The hang in step 3 is what SKIP LOCKED prevents. After step 4, window 2 returns 2. Postgres re-checked row 1 after the wait, found it no longer queued, and moved on.

Try it: a refused replay
  1. Build a small table with the partial unique index and one pending job: 
    CREATE TABLE q (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                dedupe_key text, state text NOT NULL);
CREATE UNIQUE INDEX q_pending ON q (dedupe_key)
  WHERE state IN ('queued', 'running');
INSERT INTO q (dedupe_key, state) VALUES ('fetch:42', 'queued');
  2. Run the same INSERT with ON CONFLICT DO NOTHING on the end. psql reports INSERT 0 0.
  3. Kill the job with UPDATE q SET state = 'dead' WHERE id = 1;, then run the plain INSERT again. It succeeds.
  4. Replay the dead row: UPDATE q SET state = 'queued' WHERE id = 1;.

Step 4 fails with duplicate key value violates unique constraint "q_pending". That's how the replay command knows an equivalent job is already queued.

If an interviewer asks

"Why didn't you use Celery or SQS?"

"Because I enqueue jobs in the same transaction as the data. When a fetch saves articles, the score jobs commit with them or not at all, and with SQS I'd need an outbox and a relay for that. At a thousand jobs a day Postgres has huge headroom, and jobs are rows I can query. I also wrote down when I'd switch: a p95 claim time over 50 ms in the load test moves the delivery queue to SQS first."

"What happens if a worker dies halfway through a job?"

"Its lease expires, because the heartbeats stop. The reaper counts the crashed run as an attempt. Below max_attempts the job goes back to queued with backoff, and at the limit it goes to dead with a dead letter, so a poison pill can't crash workers for ever. A stalled worker can lose its job the same way and run it twice, which is why every handler is idempotent."

"Does waiting for a rate-limited host use up a job's attempts?"

"No. The job is deferred to the host's next slot, the claim's attempt is given back, and deferrals goes up instead, so attempts only counts runs that did work. The job that actually got the 429 made a request, so its retry counts."
