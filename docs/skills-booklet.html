Briefing engine

Skills for a backend developer

The briefing engine collects news from RSS feeds, scores each article with a language model against each reader's interests, and delivers a short written briefing every morning. It is small enough for one developer to build and understand completely, yet it meets almost every problem that larger backend systems face, from duplicate work and concurrent spending to unreliable networks and unpredictable model output.

The project is at the design stage. The plan is written and reviewed, and the code is about to begin, so the skills described here are the ones the build is designed to teach.

Overview

The project and its lessons

The briefing engine replaces Horizon, an open-source news aggregator that produced a daily AI briefing from a scheduled task on a single machine. Getting Horizon to run reliably exposed three bugs: the model API rejected a parameter that the fallback code did not recognise, Reddit's feed returned 429 Too Many Requests when requests arrived in bursts, and the email's HTML was escaped twice. Each of those failures became a requirement for the new design.

The replacement is designed as one Python codebase that runs as two kinds of process, an API and a worker, with a single PostgreSQL database holding both the data and the queue of work. It will be built in three stages, each with a clear definition of done. The first stage serves one user, the second turns it into a multi-user service on AWS, and the third adds shared caching, enforced budgets, signed webhooks and a load test.

The first stage is itself split into four checkpoints: one complete briefing, then making it repeatable and recoverable, then the full daily briefing, and finally a week running alongside Horizon. Each checkpoint ends in something that can be run and inspected, so problems surface while they are still easy to trace.

Figure 1 places the skills on a map of the system. Every component teaches something, and several skills, such as reliability and testing, run through all of them.

The skills are not all learnt at once. Each stage of the build introduces a new set, as Figure 2 shows, so the project grows in difficulty at the same pace as the system grows in scope.

The thread that connects all of these skills is a single goal: the system must keep working correctly when things go wrong. That goal is where the skills begin.

Skill group

Reliability and correctness

Most of what makes the briefing engine more than a script is the work it does to stay correct when something fails. In a system with several workers, crashes, timeouts and retries are normal events, so the design has to make each of them harmless.

Idempotency

plan §2, §6.6, §5.1

An operation is idempotent when running it twice has the same effect as running it once. Every step in the briefing engine is designed this way, using upserts, unique constraints, idempotency keys and cached model results. The goal is that re-running a job, or an entire day, stores no duplicate rows, sends no second email and costs close to nothing, and the second checkpoint exists to prove it.

This is the most transferable skill in the project, because any system that retries work depends on it.

Concurrency control

plan §9.1, §7.7

Several workers run at the same time, and they must share both work and money without interfering with each other. Workers claim jobs with SELECT … FOR UPDATE SKIP LOCKED, so two of them never take the same job. A Postgres advisory lock ensures that only one copy of the scheduler runs, and a conditional UPDATE protects each user's budget when many jobs try to spend it at once.

Each job also commits its result together with the jobs that follow it, in one transaction, so a crash can never leave the system with half of a step recorded.

Failure handling

plan §6.3, §9.1, §8.3

Failures are treated as expected events, each with a response decided in advance. Requests are retried with exponential backoff and jitter. A job's lease expires if its worker dies, which lets another worker pick the job up. Work that keeps failing moves to a dead-letter table where it can be inspected and replayed.

Underneath all of this, every job moves through a state machine that always reaches a final state, so nothing is left waiting forever.

Skill group

Databases

Because PostgreSQL sits at the centre of the design, the project teaches far more about it than writing queries. The database is where most of the reliability guarantees are actually enforced.

Schema design

plan §4

A multi-user service has to decide who owns each row. Feeds, articles and scores are facts about the world, so they are stored once and shared by everyone. Rubrics, briefings, budgets and deliveries belong to individual users. This split is what keeps the cost of fetching and scoring roughly flat as more users join.

The rules that must never break, such as one briefing per user per day, are enforced by Postgres itself through constraints and partial unique indexes. A bug in the application code therefore cannot violate them.

Postgres as infrastructure

plan §6.2, §9.1, §9.2

The same database serves as the system of record, the job queue and the per-host rate limiter. Keeping everything in one place lets related changes commit together, and it removes the need to run a separate message broker.

The plan also compares the Postgres queue with Amazon SQS, and the load test measures queue contention to show when that choice should be revisited. Knowing where an approach stops being enough is as valuable as knowing how to use it.

Migrations

plan §4.3, §12.3

The schema changes as the system grows, and Alembic migrations apply those changes while the service keeps running. The readiness endpoint reports the schema version, and a deploy continues only when the database is at least at the version the new code expects. This is how teams avoid releasing code against a schema it cannot work with.

Skill group

APIs and integration

The service talks to the outside world in three directions. Clients call its API, it fetches content from servers that belong to other people, and it sends results to systems it does not control. Each direction teaches a different set of habits, and security runs through all three.

REST API design

plan §5

There is no web front end, so the API under /v1 is the whole interface. It authenticates clients with hashed API keys and scopes, and it pages through constantly growing lists with signed cursors that never repeat a row. Every error is reported in the same problem+json format.

Clients can also send an Idempotency-Key header, so a request that is retried after a timeout cannot create the same thing twice.

Being a good HTTP client

plan §6.2, §6.3, §6.4

Fetching feeds from hosts you do not control requires good manners. The fetcher limits how often it contacts each host, waits as long as a Retry-After header asks, and backs off when a host is struggling. It sends conditional requests with ETag and Last-Modified, so a feed that has not changed is not downloaded again.

These habits come from a real failure. Reddit's feed answered 429 Too Many Requests when the old system sent requests in bursts, and the briefing went out without those sources.

Webhooks

plan §8.2, §8.3

Users can receive their briefing as an HTTP request to their own server. Each request is signed with HMAC in the Standard Webhooks format, so the receiver can prove that it came from the service and was not altered on the way. Signing secrets can be rotated, and a retry schedule with dead letters and replay means that a receiver which was offline for hours still receives every event.

Security basics

plan §6.1, §7.2, §8.1

Three defences recur throughout the design. Once users can submit URLs, an SSRF guard stops the service from being tricked into fetching internal addresses, such as the endpoint that hands out cloud credentials. HTML is escaped in exactly one place, the email template, after the old system escaped it twice and showed apostrophes as &#x27;.

Finally, article text is always treated as data when it is sent to the model, which guards against prompt injection hidden in feeds written by strangers.

Skill group

Working with LLMs in production

The language model is the only part of the system that costs money on every call, the only part whose output cannot be fully predicted, and the only part that reads text written by strangers. Using it in production is therefore mostly a matter of control.

Choosing the right model for each job

plan §7.1

Claude Haiku 5.5 scores every new article, because that work is high in volume and needs to be fast and cheap. Claude Sonnet 5.5 writes the final summary, which happens once per user each day and benefits from a stronger writer.

The choice is checked with evidence. An evaluation compares the cheaper model's scores with labels assigned by hand before the split is relied on.

Structured output and validation

plan §7.3, §7.4

The model must answer in a fixed JSON shape, and the application validates every response before anything is stored. When the output is malformed or incomplete, the plan has already decided what happens next, such as splitting a batch and retrying the articles individually. A bad answer therefore never finds its way silently into a briefing.

Caching and cost control

plan §7.5, §7.7

Scores are cached by a hash of the exact text the model reads together with the rubric, so the same question is never paid for twice, and re-running a day costs almost nothing. Every call is recorded in a ledger with its token counts and cost.

From the third stage, each user also has a budget that concurrent jobs cannot overspend. Before a call is made, its maximum possible cost is reserved with a single conditional update. If a worker crashes mid-call, the reservation is counted as uncertain spend instead of being released, so the same money can never be spent twice. The guarantee depends on the estimate really being an upper bound, which the ledger checks on every call.

Skill group

Cloud and operations

The second stage moves the service from a laptop into AWS, with one firm rule: nothing is configured by hand. Everything that runs in the cloud can be recreated from code in an empty account.

Infrastructure as code

plan §11.1, §11.2

Terraform creates the whole environment. That includes ECS Fargate services for the API and the worker, an RDS PostgreSQL database in private subnets, Secrets Manager for credentials and the networking that connects them.

The plan also records why always-on containers suit this workload better than Lambda functions. Trade-offs of that kind are exactly what interviewers like to probe.

CI/CD

plan §10, §11.2

Every pull request runs linting, type checks and the test suites. Deploys authenticate to AWS through GitHub's OIDC provider, so no long-lived access keys are stored anywhere. A deploy builds the image, runs the migrations and rolls out the new version, with an approval step guarding production.

Observability

plan §12

Structured logs, metrics, worker heartbeats and CloudWatch alarms together show whether the system is healthy. A liveness endpoint serves the load balancer, and a separate readiness endpoint gates deploys.

The stage is not finished until an alarm has fired in a test and its email has arrived. That requirement proves that the monitoring works, instead of assuming it.

Skill group

Testing

The guarantees that matter most in the briefing engine are the hardest to observe, because many of them fail only under timing that rarely happens on a laptop. The testing strategy is designed to make those failures appear on demand.

Testing the hard parts

plan §10

Anything involving concurrency or database constraints is tested against a real PostgreSQL 17 instance, because a mock can only repeat your own assumptions. Property-based tests with Hypothesis search for inputs that break URL normalisation and hashing, and golden files lock down the exact HTML of the email.

Fake feed and Anthropic servers complete the picture. They reproduce slow responses, rate limits and outages whenever a test needs them, without touching any real service.

Load testing and outage drills

plan §13

A k6 load test sends a constant 50 requests per second for ten minutes, whatever the response time. Holding the arrival rate fixed stops a slow server from appearing fast simply because it received fewer requests.

Scripted drills then break the system on purpose. They stop a worker mid-run, reboot the database, make the model API fail for twenty minutes and take a webhook receiver offline for three hours. The target for every drill is that no job is lost.

Skill group

Engineering judgement

The last group of skills has less to do with code and more to do with how decisions are made, recorded and defended. It is also the group that interviewers value most.

Writing a design before the code

plan §2, §15, §16

The whole design was written down and reviewed before the first line of code. It states goals and non-goals, records each significant decision together with the options that were rejected and the reasons, and keeps an explicit list of questions that are still open.

Working this way means that every decision can be reviewed and challenged by someone else, which is how experienced teams operate.

Building in small, checkable steps

plan §14

A design review found that the first milestone bundled too many kinds of uncertainty together: a queue, ingestion, two model stages, caches, accounting and delivery recovery all had to work before the first briefing arrived. The plan now follows a working rule: settle what the next checkpoint needs, and record later decisions without building them early.

Learning to sequence work this way, so that each step produces evidence before the next one depends on it, is one of the most practical skills the project teaches.

Judging the product as well as the code

plan §14

A briefing can be delivered reliably and still be unpleasant to read. From the first email, a short reading log records what was useful, what was misleading or annoying, and one thing to change, and those notes decide what to build next. Code can check lengths, references and repeated stories, but whether a summary is faithful and whether important stories were missed still need a person's judgement.

Measuring results

plan §13

The metrics are defined before the system exists: cost per briefing before and after caching, fetches saved by conditional requests, API latency at the 95th percentile and recovery from outages. The project will end with a published case study that reports the real numbers, so every claim about the design can be checked.

Closing

Why it matters in an interview

Almost any developer can learn a library from its documentation. Far fewer can explain the decisions behind a working system and show the evidence that those decisions were right.

Building the briefing engine gives you a concrete, tested answer to the questions that separate backend engineers from developers who have only written scripts. Each answer comes from a system you designed, built and measured yourself, which makes it far more convincing than an answer learnt from a book. Questions like these become straightforward:

  1. Why did you choose a Postgres queue instead of SQS, and what would make you change your mind?
  2. What happens when a worker dies halfway through sending an email?
  3. How does a user's budget hold when twenty jobs try to spend it at the same moment?
  4. How do you stop a retried API request from creating the same resource twice?
  5. How do you know your system recovers from an outage without losing work?

Each of these has a short answer, a deeper explanation and a test or measurement behind it. That combination is what turns a portfolio project into evidence of backend engineering skill.
